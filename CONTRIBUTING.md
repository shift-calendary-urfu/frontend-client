# Регламент работы с Git и ветками в проекте
## Является **ПРЕДЛОЖЕНИЕМ** для работы для исключения возможных серьезных конфликтов. На деле решайте сами, но ответственность также лежит на вас!

Пожалуйста, соблюдайте правила этого регламента.  
Особенно важны разделы **2.1** и **2.2**.

## 1. Структура и назначение веток

В репозитории используется фиксированная структура веток.  
Создание веток, не соответствующих правилам именования, запрещено.

### `main` — основная ветка

- **Статус:** стабильный production-код.
- **Правило:** прямые коммиты в `main` и слияние личных веток напрямую в `main` запрещены.
- Код попадает в `main` только из ветки `dev` при выпуске официального релиза.

### `dev` — основная ветка разработки

- **Статус:** среда для сборки готовых фич и тестов.
- **Правило:** `dev` является основной веткой для интеграции.
- Все разработанные фичи и тесты вливаются в `dev` только через Pull Request.
- Прямые коммиты в `dev` запрещены.

### `feature-<name>` — ветки для разработки функциональности

- **Правило:** создаются строго от актуальной ветки `dev`.
- Название должно отражать суть фичи, например:
  - `feature-billing-stripe`
  - `feature-auth-jwt`
- **Куда вливается:** обратно в `dev`.

### `test-<name>` — ветки для написания тестов

- **Правило:** создаются от ветки `dev` либо от конкретной feature-ветки, если тесты пишутся параллельно с разработкой.
- Название должно отражать, что именно тестируется, например:
  - `test-api-endpoints`
  - `test-database-queries`
- **Куда вливается:** в `dev` или в родительскую feature-ветку.

## 2. Пошаговый рабочий процесс

### 2.1. Начало работы

Перед созданием новой ветки всегда обновляйте локальную ветку `dev`, чтобы уменьшить вероятность конфликтов:

```bash
git checkout dev
git pull origin dev
```

Создайте свою ветку от обновлённого `dev`:

```bash
# Для разработки фичи
git checkout -b feature-my-awesome-feature

# Для написания тестов
git checkout -b test-my-new-tests
```

### 2.2. Разработка и коммиты

Пишите код и делайте атомарные, понятные коммиты.

Перед отправкой ветки в удалённый репозиторий убедитесь, что она не отстала от `dev`:

```bash
git fetch origin
git merge origin/dev
```

Если возникли конфликты, разрешите их локально в своей ветке.

> **Важно:** не используйте `git rebase`, если это не согласовано отдельно.

### 2.3. Работа через интерфейс GitHub

Вместо работы с Git через терминал можно использовать встроенные инструменты IDE или интерфейс GitHub.

Принцип остаётся тем же:

1. Создайте ветку от актуальной `dev`.
2. Внесите изменения и сделайте коммиты.
3. Отправьте ветку в удалённый репозиторий.
4. Откройте Pull Request с целевой веткой `dev`.
5. Обновите ветку свежим `dev`, если он изменился.
6. Разрешите конфликты, если они появились.
7. Проверьте изменения и нажмите **Merge pull request**.

#### Создание Pull Request через GitHub

1. Перейдите на страницу репозитория в GitHub.
2. Нажмите **Pull requests** → **New pull request**.
3. В поле `base` выберите `dev`.
4. В поле `compare` выберите свою ветку, например `feature-my-awesome-feature`.
5. Убедитесь, что GitHub не показывает непреднамеренных изменений и что целевая ветка — именно `dev`.
6. Добавьте понятный заголовок и описание изменений.
7. Нажмите **Create pull request**.

#### Обновление ветки через GitHub

Если в `dev` появились новые изменения, обновите свою ветку перед merge:

1. Откройте свой Pull Request.
2. Если GitHub предлагает кнопку **Update branch**, нажмите её.
3. Если появились конфликты, нажмите **Resolve conflicts**.
4. Исправьте конфликты в редакторе GitHub, сохраните изменения и продолжите merge.

Альтернативно можно обновить ветку локально:

```bash
git checkout feature-my-awesome-feature
git fetch origin
git merge origin/dev
git push origin feature-my-awesome-feature
```

#### Merge через интерфейс GitHub

После самопроверки откройте вкладку **Conversation** в Pull Request и нажмите:

```text
Merge pull request
```

Затем подтвердите слияние.

Использование терминала для merge **не обязательно**: допускается выполнять merge непосредственно через кнопку **Merge pull request** в интерфейсе GitHub.

## 3. Самопроверка перед merge

У нас нет выделенного ревьюера, который будет исправлять ошибки за автором.  
Ответственность за работоспособность кода лежит на его авторе.

Перед нажатием **Merge pull request** необходимо тщательно проверить изменения.

### Что нужно проверить

1. **Локальный запуск.**  
   Проект с вашими изменениями компилируется, запускается и стабильно работает локально. Ничего не падает.

2. **Анализ diff.**  
   Откройте вкладку **Files changed** в Pull Request на GitHub и внимательно прочитайте все изменения.

3. **Удаление мусора.**  
   Убедитесь, что в коде не осталось:
   - отладочных `print`, `console.log` и логов;
   - закомментированных кусков старого кода;
   - временных заглушек;
   - тестовых данных и отладочных файлов;
   - ненужных изменений форматирования.

4. **Проверка логики.**  
   Задайте себе вопрос: «Не сломает ли этот код существующий функционал? Учтены ли крайние случаи, ошибки авторизации, запросов и обработки данных?»

Только после полной проверки код можно вливать в `dev`.

## Чек-лист перед нажатием Merge

- [ ] Моя ветка создана от `dev`, а не от `main`.
- [ ] В Pull Request целевой веткой (`base`) указана `dev`.
- [ ] Моя ветка содержит актуальный `dev`, конфликты разрешены.
- [ ] Я лично просмотрел все изменения на вкладке **Files changed**.
- [ ] В коде нет отладочных выводов, временных заглушек и закомментированного старого кода.
- [ ] Проект локально запускается и работает корректно.
- [ ] Я уверен, что после merge ветка `dev` останется рабочей и стабильной.
- [ ] Я нажал **Merge pull request** в GitHub либо выполнил merge через терминал.
