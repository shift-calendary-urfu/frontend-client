# Управление сотрудниками

Реализованы создание, редактирование, удаление с подтверждением и просмотр сотрудников. Список доступен в описании ПВЗ, редакторе ПВЗ и разделе «Сотрудники» нижнего меню. В разделе меню выбирается рабочая точка; отображаются все её активные сотрудники без искусственного ограничения количества.

## Как проверить вручную

1. Запустите backend и frontend по основному README. Войдите как владелец и создайте ПВЗ с непустым адресом.
2. В другом браузере или окне инкогнито зарегистрируйте аккаунт сотрудника. Нужен его точный телефон из аккаунта: `+7XXXXXXXXXX` и `8XXXXXXXXXX` backend сравнивает как разные строки.
3. В сессии владельца откройте описание ПВЗ → «+» у сотрудников. Укажите телефон, роль «Сотрудник» или «Администратор», при необходимости должность → «Создать».
4. Проверьте, что сотрудник появился в описании ПВЗ и в разделе «Сотрудники» нижнего меню при выборе той же точки. Обновите страницу — запись должна сохраниться.
5. Нажмите карандаш у сотрудника. Измените роль и должность → «Сохранить». В обоих списках должны отображаться свежие данные.
6. Откройте редактирование → «Удалить сотрудника». Проверьте отмену, затем подтвердите удаление. Запись пропадёт из обоих списков, аккаунт пользователя сохранится. Повторное добавление того же телефона восстанавливает запись на backend.
7. Войдите сотрудником: доступны просмотр точки и списка, кнопок управления нет. После назначения администратором доступны создание, редактирование и удаление сотрудников этого ПВЗ. Изменять сам ПВЗ по-прежнему может только владелец.
8. Проверьте неизвестный телефон, повторное добавление активного сотрудника, отключённый backend и ширины окна 320/393/768 px. При ошибке форма должна сохранять введённые данные, при ожидании запроса — блокировать повторную отправку.

## Контракт API

Контракт описан в `docs/openapi_231026.json` и исходниках актуального backend. Авторизация — `Authorization: Bearer <access_token>`, существующее обновление токенов сохранено.

| Действие                | Запрос                                              | JSON запроса                | Ответ                                                    |
| ----------------------- | --------------------------------------------------- | --------------------------- | -------------------------------------------------------- |
| Добавить                | `POST /employees/?workplace_id={id}`                | `phone`, `role`, `position` | `201`, `EmployeeResponse`                                |
| Прочитать для формы     | `GET /employees/{employee_id}?workplace_id={id}`    | Нет                         | `200`, `EmployeeResponse`                                |
| Изменить                | `PUT /employees/{employee_id}?workplace_id={id}`    | `role`, `position`          | `200`, `EmployeeResponse`                                |
| Удалить из точки        | `DELETE /employees/{employee_id}?workplace_id={id}` | Нет                         | `200`, `{"message":"Employee deactivated successfully"}` |
| Список в меню           | `GET /workplaces/{id}/employees`                    | Нет                         | `200`, массив сотрудников                                |
| Список в описании точки | `GET /workplaces/{id}`                              | Нет                         | `200`, точка с массивом `employees`                      |

`workplace_id` обязателен в query каждого запроса `/employees`, включая GET/PUT/DELETE. В теле создания нет `name`, `user_id`, `workplace_id` или `hire_date`. Имя, фамилия и телефон берутся из вложенного `user`; дата найма назначается сервером. Пустая должность отправляется как `null`, длина ограничена 100 символами по модели БД.

Создание привязывает **существующий зарегистрированный аккаунт** к одной точке. Свободный ввод имени, редактирование чужого телефона и назначение сразу нескольких точек в этой форме отсутствуют, потому что текущий API этого не поддерживает. Для работы человека в нескольких точках добавьте его отдельно в каждую.

Права управления определяются по `point.owner_id === me.id` или активной записи текущего пользователя с ролью `admin` в этой точке. Строка `owner` в записи сотрудника сама по себе не передаёт владение точкой. Создание предлагает роли из макета — администратор и сотрудник; при редактировании существующей записи с `owner` её роль можно сохранить. Backend повторно проверяет права при каждом запросе.

После успешной записи приложение возвращается в исходный раздел и заново запрашивает данные. После снятия с себя роли администратора кнопки управления исчезают. При удалении администратором собственной записи приложение переходит к доступным точкам; его аккаунт остаётся активным.

Обрабатываются ошибки сети и ожидание ответа, `401` с обновлением сессии, `403`, `404`, `409`, `422` и `5xx`. При утрате прав или удалении записи во время редактирования повторная запись блокируется. При быстрой смене ПВЗ запоздалый ответ предыдущей точки не подменяет текущий список.

## Маршруты frontend

| URL                                                     | Назначение                            |
| ------------------------------------------------------- | ------------------------------------- |
| `/employees?workplace={id}`                             | Список сотрудников выбранного ПВЗ     |
| `/workplaces/{id}`                                      | Описание точки и сотрудники           |
| `/workplaces/{id}/edit`                                 | Редактор точки со списком сотрудников |
| `/workplaces/{workplaceId}/employees/new`               | Добавление сотрудника в точку         |
| `/workplaces/{workplaceId}/employees/{employeeId}/edit` | Изменение и удаление сотрудника       |

Параметр `from` принимает только `employees`, `workplace`, `workplace-edit` и задаёт возврат в исходный раздел. Произвольные адреса возврата не используются. Новые формы требуют сессию; на них скрыта нижняя панель, как в макете.

## Проверки

Тесты frontend проверяют списки, создание, редактирование, подтверждение и отмену удаления, права владельца/администратора/сотрудника, URL и JSON запросов, восстановление записи и обработку ошибок.

Запуск проверок описан в основном [README](../README.md). Vitest использует подменённые ответы API; сценарий выше проверяйте также с запущенным backend. Визуально проверьте ширины 320/393/768 px.
