# Инструкция по интеграции WebSocket чата

## 1. Подключение

**Endpoint:**

```text
ws://<BACKEND_HOST>/chats/ws
```

Для HTTPS-окружения необходимо использовать `wss://`.

Пример для локальной разработки:

```text
ws://localhost:8000/chats/ws
```

WebSocket использует JWT-аутентификацию. Токен передаётся не в URL и не в заголовке, а первым JSON-сообщением после подключения.

## 2. Авторизация

После открытия WebSocket-соединения необходимо отправить:

```json
{
  "type": "auth",
  "token": "<ACCESS_TOKEN>"
}
```

Где `ACCESS_TOKEN` — действующий access JWT, полученный при авторизации пользователя.

**Важные условия:**
- Авторизация должна быть отправлена в течение 5 секунд после подключения.
- Refresh-токен использовать нельзя.
- Пользователь должен существовать и иметь `is_active = true`.
- При успешной авторизации сервер не отправляет отдельное подтверждающее событие. Можно переходить к отправке сообщений.
- При ошибке авторизации соединение закрывается с кодом `4003`.

## 3. Отправка сообщения

После успешной авторизации клиент может отправлять сообщения.

Формат события:

```json
{
  "type": "message",
  "chat_id": 1,
  "text": "Привет! Как дела?"
}
```

Поля:

| Поле | Тип | Описание |
|---|---|---|
| `type` | string | Тип события — `message` |
| `chat_id` | integer | ID чата |
| `text` | string | Текст сообщения |

**Ограничения:**
- Длина сообщения — от 1 до 4000 символов после удаления пробелов по краям.
- Пустые сообщения не принимаются.
- Частота отправки — не более одного сообщения в секунду на пользователя.
- Нельзя отправлять сообщения в чат, к которому у пользователя нет доступа.
- В закрытый Workplace нельзя отправлять сообщения.

## 4. Получение нового сообщения

После успешного сохранения сообщения сервер рассылает участникам чата событие:

```json
{
  "type": "new_message",
  "data": {
    "id": 15,
    "chat_id": 1,
    "sender_id": 3,
    "sender_name": "Иван Иванов",
    "text": "Привет! Как дела?",
    "created_at": "2026-11-18T16:30:00+00:00"
  }
}
```

Структура `data`:

| Поле | Тип | Описание |
|---|---|---|
| `id` | integer | ID сообщения |
| `chat_id` | integer | ID чата |
| `sender_id` | integer / null | ID отправителя |
| `sender_name` | string | Имя отправителя |
| `text` | string | Текст сообщения |
| `created_at` | datetime | Дата и время создания |

Событие `new_message` используется для обновления интерфейса чата.

Не нужно самостоятельно добавлять отправленное сообщение в историю до получения подтверждения `new_message`: сервер рассылает его в том числе подключению отправителя.

## 5. Heartbeat: Ping / Pong

Для проверки активности соединения сервер самостоятельно отправляет событие:

```json
{
  "type": "ping"
}
```

Клиент должен ответить:

```json
{
  "type": "pong"
}
```

Правила:
- Сервер отправляет `ping` каждые 30 секунд.
- После получения `ping` клиент должен отправить `pong`.
- Если сервер не получает `pong` в течение 60 секунд, соединение закрывается с кодом `4000`.

Важно: `pong` необходимо отправлять именно в ответ на `ping`, а не периодически самостоятельно.

## 6. Обработка ошибок

Сервер отправляет ошибки в следующем формате:

```json
{
  "type": "error",
  "detail": "Описание ошибки"
}
```

Возможные ситуации:

| Ситуация | Результат |
|---|---|
| Неверный формат сообщения | `error` |
| Неизвестный тип события | `error` |
| Пустой текст | `error` |
| Текст длиннее 4000 символов | `error` |
| Нет доступа к чату | `error` |
| Чат доступен только для чтения | `error` |
| Превышен лимит отправки | `error`, `detail: "rate_limit"` |
| Внутренняя ошибка сервера | `error` |

При `rate_limit` необходимо подождать перед следующей отправкой сообщения.

Ошибки бизнес-логики не обязательно закрывают соединение. После получения `error` клиент может продолжить работу с WebSocket.

## 7. Закрытие соединения

| Код | Причина |
|---|---|
| `4000` | Клиент не ответил на `ping` в течение 60 секунд |
| `4003` | Ошибка авторизации или истечение JWT |

При закрытии соединения клиенту необходимо:
1. Обновить состояние подключения в интерфейсе.
2. При необходимости выполнить повторное подключение.
3. Повторно пройти авторизацию с актуальным access JWT.

## 8. Пример клиентской реализации

Пример на JavaScript:

```javascript
const socket = new WebSocket("ws://localhost:8000/chats/ws");

socket.onopen = () => {
    socket.send(JSON.stringify({
        type: "auth",
        token: accessToken
    }));
};

socket.onmessage = (event) => {
    const data = JSON.parse(event.data);

    switch (data.type) {
        case "ping":
            socket.send(JSON.stringify({
                type: "pong"
            }));
            break;

        case "new_message":
            console.log("Новое сообщение:", data.data);
            // Обновить историю сообщений
            break;

        case "error":
            console.error("Ошибка:", data.detail);
            break;
    }
};

socket.onclose = (event) => {
    console.log("Соединение закрыто:", event.code);
};

socket.onerror = (error) => {
    console.error("Ошибка WebSocket:", error);
};

// Отправка сообщения
function sendMessage(chatId, text) {
    if (socket.readyState !== WebSocket.OPEN) {
        return;
    }

    socket.send(JSON.stringify({
        type: "message",
        chat_id: chatId,
        text: text
    }));
}
```

Это пример базового взаимодействия. В рабочем frontend необходимо также учитывать состояние авторизации, переподключение и жизненный цикл компонента.

## 9. Сценарий проверки работоспособности

Рекомендуется проверить следующие сценарии:

1. Подключиться к WebSocket с действующим access JWT.
2. Подключиться с неверным токеном — ожидать закрытие `4003`.
3. Отправить сообщение в существующий чат.
4. Убедиться, что сообщение появляется у отправителя и второго участника.
5. Открыть два подключения одного пользователя и проверить получение сообщений в обоих.
6. Отправить два сообщения с интервалом менее секунды — второе должно получить `rate_limit`.
7. Отправить пустое сообщение — получить `error`.
8. Дождаться `ping` и проверить автоматическую отправку `pong`.
9. Отключить клиент и проверить корректное завершение соединения.

**Важно:** WebSocket отвечает только за обмен новыми сообщениями в реальном времени. Загрузка истории, получение списка чатов и отметка сообщений прочитанными выполняются через REST API. Их контракты доступны в OpenAPI документации backend.
